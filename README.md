# open-gajae

**A personal learning and toy project built as a plugin for OpenCode v2.** OpenCode v1 is not supported.

## Background and project status

I enjoyed using [gajae-code](https://github.com/Yeachan-Heo/gajae-code) and [oh-my-claudecode (OMC)](https://github.com/Yeachan-Heo/oh-my-claudecode), and wanted a similar experience in an environment where I could only use OpenCode. I started open-gajae to explore that possibility and learn how to develop coding agents, drawing on both projects as references. I also studied [oh-my-openagent (OMO)](https://github.com/code-yeongyu/oh-my-openagent) as a reference for OpenCode plugin development and host integration. Many thanks to the authors and contributors of all three projects for the inspiration and work shared with the community.

This is an independent, unofficial project. It is not affiliated with or endorsed by gajae-code, OMC, OMO, or OpenCode/Anomaly, and is not an official port or compatibility layer for gajae-code, OMC, or OMO. It does not guarantee the same features, behavior, or compatibility as those projects. Its purpose is personal learning and experimentation.

For retained and adapted third-party material, see [third-party notices](THIRD-PARTY-NOTICES.md). [Banner credits](assets/branding/open-gajae-banner.md).

## Overview

An OpenCode plugin with session-bound `deep-interview`, `ralplan`, and `ultragoal` skills, a `goal` tool, nine owned roles, and a small read-only code-research surface. The main-agent prompt, the `deep-interview` skill with its runtime and its lateral-review panel, the `ralplan` skill with its runtime and its three consensus roles, and the `ultragoal` skill with its runtime, the `goal` tool, and the cleaner role are adapted from GJC; the explore, document-specialist, and executor roles retain their OMC-derived contracts, and so does ultragoal's progress log format. It is **not** a full OMC or GJC port; its one execution workflow is `ultragoal`, rebuilt on GJC's ultragoal and goal mode.

## Scope and status

- Phase 1, the OMC-baseline port, was closed by the maintainer on 2026-09-27. Phase 2 improvements are maintainer decisions with gajae-code as the primary reference; the policy is in [AGENTS.md](AGENTS.md).

- The target host is OpenCode v2. This port targets `@opencode/plugin` 2.0.15 against the local `opencode/` reference pinned to `v2.0.15` (`6f3639d82e`); a v1 host can no longer load this plugin (v1 support is dropped — see the deviations table).
- The package is TS source with no build step: `package.json` `exports["."]` points at `./src/index.ts`, and the root `index.ts` re-exports it. There is no `dist/`.
- Implemented scope: `deep-interview`, `ralplan`, and `ultragoal`; `open-gajae`, `open-gajae-explore`, and `open-gajae-document-specialist`; the `open-gajae-planner`, `open-gajae-architect`, and `open-gajae-critic` consensus roles; the `open-gajae-executor` and `open-gajae-cleaner` ultragoal-execution roles; the `open-gajae-lateral-reviewer` deep-interview panel role; session state; and twelve directly-callable tools (the `deep-interview`, `ralplan`, `ultragoal`, and `goal` tools, and eight read-only AST/LSP tools).
- `ralplan` is implemented and ends at a plan marked `pending approval` (`pending-approval.md`), whose final approval step offers `Refine further`, `Approve execution via ultragoal (Recommended)`, or `Stop here`. `ultragoal` is implemented on GJC's ultragoal runtime and goal mode: a durable goal list with acceptance criteria, a ledger with completion receipts, an architect gate on every goal, a boundary review cohort (cleaner, architect, executor QA/red-team) and a terminal critic at the run's final goal, and the `goal` tool's continuation loop (see [Ultragoal](#ultragoal)); the deep-interview → ralplan → ultragoal handoff chain, the direct deep-interview → ultragoal handoff, and the handoffs from ultragoal and ralplan back to deep-interview are provided. Not provided: autopilot, team, a standalone `ralph` skill, autoresearch, shared session state, or automatic migration/recovery. No slash commands exist; explicit natural-language requests and supported mentions or keywords can enter a skill (see Entry, below).
- The v2 host and workflow description originated on `feat/opencode-v2-port` at commit `f4df6e6`; the main-agent prompt baseline above is a separate change. That change did not by itself establish Phase 1 completion, and it does not assert that the verification layers below (typecheck, unit tests, host probes) pass for that change — see the plan for its checks.

## Install (OpenCode v2)

```sh
bun install
bun run typecheck
bun test ./tests
```

Add a `plugins` entry pointing at this repository's **directory** (not a built file) to the host config, typically `~/.config/opencode/opencode.jsonc`:

```jsonc
{
  "plugins": ["/Users/dongwuk/apps/open-gajae"],
  "default_agent": "open-gajae",
  "experimental": { "subagent_depth": 2 }
}
```

- `plugins` must be a directory path. The v2 host resolves `<dir>/server`, then `<dir>/index`, with extension inference, and skips a configured plugin path that is a file — even though some host docs show file-path examples (a recorded docs/implementation mismatch). This package's root `index.ts` re-exports `./src/index.ts`, so the host loads TypeScript source directly with no build step.
- `experimental.subagent_depth: 2` is required for the `open-gajae-planner` role to delegate research to `open-gajae-explore`/`open-gajae-document-specialist` through the native `subagent` tool. The plugin cannot set this itself — v2's plugin API has no config-mutation domain, unlike v1 — so it is a host setting you add yourself. The GJC-based planner prompt gives no delegation instructions, so delegating is the model's choice; without this setting the host refuses the planner's `subagent` call and the planner researches with `read`/`grep`/`glob` itself.
- `default_agent: "open-gajae"` makes the primary role the default for new sessions. Optional but recommended.
- This is not a full replacement config; keep the rest of the file and add only these keys. The plugin never edits host configuration.

This is a summary; see [`docs/local-install-v2.md`](docs/local-install-v2.md) for a full step-by-step walkthrough with a verification checklist, and [`docs/local-install-v1.md`](docs/local-install-v1.md) for the superseded v1 setup this replaces (kept as history).

Once a first prompt has been sent in this directory (plugin `setup` runs lazily, on the first prompt in a location, not at server start), inspect the installed surface with `GET /api/plugin` (confirms the plugin id and its `index.ts` source path) or `opencode debug agent <id>` / `opencode debug skill`.

## Entry

No slash commands exist in this port; v1's `/deep-interview` and `/ralplan` are gone (a recorded deviation). A direct natural-language request to use `deep-interview`, `ralplan`, or `ultragoal` runs the requested skill, as do supported mentions and invocation-context keywords:

- **Mention:** type `@deep-interview`, `@ralplan`, or `@ultragoal` and pick it from the TUI's autocomplete. Selecting it attaches the skill directly; typing the text without selecting the suggestion sends plain text with no attached skill, since the server does not parse `@` mentions itself — the keyword path below is what picks that up instead.
- **Keyword:** the same OMC-derived keyword detection as v1 (English/Korean/Japanese forms, exclusion of questions/quotes/code blocks, and ralplan's invocation-context requirement) recognizes an explicit request from plain text and injects a notice. A heuristic suggestion when no skill was requested instead offers the skill or direct work and follows the user's choice. Ordinary clarification can still happen without starting `deep-interview`. Once a skill starts, its own questions, completion choices, and approval steps still apply.
- **Ultragoal:** the `ultragoal` keyword and an `@ultragoal` mention only add a notice asking the model to load the skill; the native `skill` call with id `ultragoal` is what enters it and starts goal planning (see [Ultragoal](#ultragoal)). While ultragoal is the active skill, `@ralplan`, `@deep-interview`, and their keywords get a notice to call `ultragoal handoff` first instead.
- **Deep-interview:** the keyword, an `@deep-interview` mention, and the `skill` load only notify or attach the skill; the interview starts when the primary calls `deep-interview start` (see [Deep interview](#deep-interview)).

## Deep interview

`deep-interview` is requirements clarification rebuilt on GJC's deep-interview skill and runtime at the GJC pin: `skills/deep-interview/SKILL.md`, the `deep-interview` tool in `src/deep-interview-runtime/`, the `open-gajae-lateral-reviewer` role, whose prompt is GJC's panel fragment `lateral-review-panel.md`, and the shared skill-state base (active rows, snapshot, audit, journaled handoff, doctor) in `src/skill-state/`. It replaced the OMC-derived deep-interview and the former `state_*` tools. Every difference from GJC is recorded in [Deviations from GJC (deep-interview)](#deviations-from-gjc-deep-interview). The design decisions are in `.omc/specs/deep-interview-deep-interview-gjc-revision.md` (its Errata E1–E20 take precedence), `.omc/plans/ralplan-deep-interview-gjc-revision.md`, and `.omc/plans/deep-interview-gjc-pq-decisions.md`. How the implementation works, step by step, is in [`docs/skills/deep-interview/`](docs/skills/deep-interview/README.md).

**Entry.** A `@deep-interview` mention or one of the keywords `deep interview`, `deep-interview`, `딥인터뷰`, `ディープインタビュー`, `ouroboros` injects OMC's `[MAGIC KEYWORD: DEEP-INTERVIEW]` guide at most once; as in OMC, informational contexts (questions, quoted or referenced mentions, code, tables, block quotes) and a message starting with the `ouroboros`/`ooo` CLI form are ignored. Neither they nor a `skill` load write state: the interview starts when the primary calls `deep-interview start(idea, threshold?)` (deviation 13). The skill uses native `question` one question at a time; a completed spec is not authorization to implement it.

**Threshold.** The default ambiguity threshold is gjc's `0.05`; `deepInterview.ambiguityThreshold` in the settings files (in `(0, 1]`) overrides it, and `start(threshold)` overrides both. The resolved value and its source — `~/.open-gajae/open-gajae.jsonc`, `./.open-gajae/open-gajae.jsonc`, or `default` — reach the primary in the `<open-gajae-runtime-settings>` block; `start` records the same source string, or `start(threshold)` for an explicit value (deviation 20). The skill's first line is `Deep Interview threshold: <percent> (source: <source>)`; an active interview keeps its own threshold, and the skill never `start`s over an active state.

**Rounds and ambiguity.** After each answer the model records the round with `deep-interview write`: the question and the answer as asked, the scores, and its raw ambiguity, merged by `round_key` (`round-<n>`) as GJC merges rounds (deviation 3). The runtime checks every round it touched (`round`, `round_key`, `lifecycle: "scored"`, `question_text`, `answer`, `ambiguity`, and the goal/constraints/criteria scores; brownfield adds `context`; Round 0 is `answered`) and refuses the whole `write` when one does not match (deviation 36). `current_ambiguity` is runtime-owned: it comes from the latest scored round, clamped to a floor of `0.10` per unresolved disputed fact plus `0.05` per unscored active component (deviation 4). Transcript fields at the top level of a `write` input are refused, not moved into `state` (deviation 25). The interview ends at the threshold (after its closure and restate gates), at an early exit from round 3, on a stop request, or at a fixed 100-round cap; it does not ask whether to continue after ordinary rounds.

**Spec and handoff.** `deep-interview spec(content | path, slug?)` writes `specs/deep-interview-<slug>.md`, appends `specs/deep-interview-index.jsonl`, records `spec_path` and `spec_sha256`, and moves the interview to `handoff`. Phase 5 then offers four options: refine with ralplan (recommended), execute with ultragoal (only for an implementation-ready, very simple spec), refine further, or finish here (`deep-interview clear`) (deviation 10). Choosing ralplan or ultragoal calls `deep-interview handoff(to)` — it needs phase `handoff` and a spec file that still matches its sha256 — and then loads the skill; `spec(…, handoff: "ralplan")` does all three steps in one call (deviation 38). Loading `skill` `ralplan` or `ultragoal` in the execution that loaded deep-interview passes a gate: it refuses an interview still `interviewing`, hands off one on `handoff`, and links a finished one that has a valid spec (deviation 31). `ralplan handoff(to="deep-interview")` and `ultragoal handoff(to="deep-interview")` reopen the interview on `interviewing` with its rounds and spec fields kept.

**Guards and continuation.** While deep-interview is the visible primary skill, active on `interviewing` or `handoff`, `write`, `edit`, and `patch` outside an OS temp path are refused for every agent of the session (shell is not classified, deviation 14), and `specs/deep-interview-*` is always refused to the edit tools (deviation 35). On the root's `succeeded` the plugin continues an `interviewing` interview at most twice per real user prompt (`open-gajae: deep-interview continuation N/2`), before and instead of the goal and ralplan continuations; on `handoff` it holds both (deviation 16). When the user stops the interview, the skill cancels it with `deep-interview state(patch={"active": false})`, which ends the guard and the continuation and keeps the rounds; loading the skill again offers to resume it with `{"active": true}`. After the spec, a stop is `deep-interview clear`, as Finish here (deviation 30). Compaction adds a `<deep-interview-compaction-context>` block (deviation 15). The `deep-interview` tool belongs to `open-gajae` alone and is hidden from every other agent (deviation 24).

**Storage.** All files belong to the session lineage's root session:

```text
<worktree>/.open-gajae/
  _session-<created>-<session-id>/
    state/deep-interview-state.json
    state/active/deep-interview.json
    state/skill-active-state.json
    state/audit.jsonl
    specs/deep-interview-<slug>.md
    specs/deep-interview-index.jsonl
```

Each session owns one directory named `_session-<YYYYMMDD-HHMMSS>-<session id>`, where the label is the session's creation time in local time and the ID is the native session ID verbatim; afterwards the directory is found by its session-ID suffix, and two directories with the same suffix are an error. The state is GJC's envelope (`skill`, `version`, `active`, `current_phase` — `interviewing`, `handoff`, `complete` — `threshold`, `threshold_source`, the `spec_*` fields, and the interview under `state`) plus the StateStore `_meta`; there is no receipt, checksum, revision, or staged draft (deviation 2). Every op runs in the session's one workflow queue, checks everything before its first write, and writes one audit row per file change; the combined spec call's three steps run in order and a later failure leaves the earlier steps' results (see [`docs/skills/deep-interview/`](docs/skills/deep-interview/README.md)).

| Op | Input | Effect |
|---|---|---|
| `start` | `idea`, `threshold?` | Seeds a new interview over any previous state (the spec files stay); refused while ralplan or ultragoal is the visible primary skill (deviation 12). |
| `write` | `input`, `reset?` | Merges rounds, facts, and context into an active interview; `reset` rebuilds the state from the input alone. |
| `spec` | `content` or `path`, `slug?`, `handoff?` | Persists the final spec and moves to `handoff`; with `handoff: "ralplan"` also seeds ralplan and hands off. |
| `handoff` | `to` (`ralplan`, `ultragoal`) | The journaled handoff of an interview on `handoff` with a verified spec. |
| `status` | `fields?` | GJC's `{skill, state, storage_path}`, or the projected fields. |
| `doctor` | — | GJC's doctor text over the deep-interview state, row, and snapshot. |
| `state` | `patch` | Merges a patch (`null` deletes); rounds, facts, ambiguity, and spec fields are refused (deviation 19); the phase follows GJC's table. `{"active": false}` cancels the interview, keeping its rounds; `{"active": true}` resumes one cancelled on `interviewing`, refused like `start` while ralplan or ultragoal is the visible primary skill (deviation 30). |
| `clear` | `force?` | Sets `{active: false, current_phase: "complete"}`, keeps the spec files, removes the row; works without a state too. Without `force` it refuses a corrupt state, a state already in a release phase other than `inactive` (such as `complete`), and an active row whose phase differs from the state's (GJC `describeStaleClearState`). |

`write`, `spec`, `handoff`, and `state` need an active interview, except that `state(patch={"active": true})` resumes one cancelled on `interviewing` (deviation 30). A user may still name another session's spec or plan as an input; native Read and its permissions apply, the session reports the path it read, and nothing — state, owner, approval, or permission — transfers.

## Ralplan

`ralplan` is consensus planning rebuilt on GJC's ralplan skill and runtime contract at the GJC pin: `skills/ralplan/SKILL.md`, the `open-gajae-planner`, `open-gajae-architect`, and `open-gajae-critic` prompts, and the `ralplan` tool in `src/ralplan-runtime/`. It is planning only: the plan stays `pending approval` until the user approves execution. Every difference from GJC is recorded in [Deviations from GJC (ralplan)](#deviations-from-gjc-ralplan).

A `@ralplan [--interactive] [--deliberate] <task>` mention, or the `ralplan`/`랄플랜` keyword, starts consensus planning. As in OMC, the keyword only activates in an invocation context: a direct prefix (`$ralplan`, `!ralplan`, `force: ralplan`), an activation verb (`use`, `run`, `start`, `please`, `let's`), or the keyword at the start of the message. Questions, quoted or referenced mentions, and text inside code, tables, or block quotes do not activate it. Only the `open-gajae` primary, or a session with no agent, gets the keyword and mention notices. The host's `build` and user-defined agents get none because the `ralplan` tool is hidden from and refused to them (R-OD20); the owned role subagents get none because a role's brief can quote a keyword. When one message carries both the ralplan and the deep-interview keywords, both notices are injected, ralplan first.

A keyword turn injects a `[MODE: RALPLAN]` notice asking the model to load the `ralplan` skill. A `@ralplan` mention injects its own `[MODE: RALPLAN]` notice saying the skill is already attached, so the insertion is visible (the TUI shows `open-gajae: ralplan mention notice added`). Neither writes ralplan state: there is no seed, confirmation step, or stale-seed cleanup. The run starts when the primary calls `ralplan start`, the documented entry (GJC's `gjc ralplan "<task>"`).

Notices — the ralplan and ultragoal notices, the deep-interview magic guide, the goal hold notice, and the breaker message — are written as `ctx.session.synthetic({ resume: false })` messages, after any state write that goes with them. The host places a synthetic message **before** the user's message in the same turn, unlike OMC/v1, which appended it after (a recorded host-placement deviation, not a design choice). If `synthetic` itself fails, the notice is appended, marker-wrapped, to the prompt text instead, so it is never silently lost; the state write is kept either way.

**The `ralplan` tool** is the only writer of the ralplan state, the run's stage files, and the ralplan active row and snapshot; the former `state_*` tools are gone, and deep-interview has its own `deep-interview` tool. Its ops mirror GJC's CLI and state verbs:

| Op | Callers | Effect |
|---|---|---|
| `start(task, interactive?, deliberate?, run_id?)` | primary | Writes a fresh state (`active: true`, phase `planner`, `mode` short or deliberate) and returns a receipt with `session_id`, `run_id`, `state_path`, and `repository_binding`. Refused while the ultragoal state is active; the refusal names `ultragoal handoff(to="ralplan", reason)`. |
| `write(stage, stage_n, content \| path, run_id?, lane_verdict?, resumable?, fallback_*)` | primary, planner, architect, critic | Persists one stage artifact and returns a plain receipt (`path`, `sha256`, `stage`, `stage_n`, …). |
| `status(fields?)` | primary, planner, architect, critic | Returns `{skill, state, storage_path}`; `fields` projects state fields. |
| `doctor` | primary | Reports `schema_violation` and `stale_active_state`; changes nothing. |
| `state(patch)` | primary, planner, architect, critic | Merges a patch (`null` deletes a field); a phase change must follow GJC's transition table. Stop here is `patch={"active": false}`. |
| `handoff(to="ultragoal")` | primary | Hands the approved plan to ultragoal (below). |
| `clear(force?)` | primary | Sets `{active: false, current_phase: "complete"}` and keeps the files and `run_id`. Without `force` it refuses, as GJC does, a corrupt state, a state already in a terminal release phase (such as `complete`), and a state on an unlocked phase whose active-row phase differs from it (on a locked phase such as `final`, GJC reads the row's phase as the state's, so a clear during post-final refinement goes through); an unreadable active-row file also stops it (deviation 35). |

Every op acts on the calling session's lineage root, so a role's child session writes into the root session's folder. The run folder is the explicit `run_id`, then the state's `run_id`, then the root session's native ID (for example `ses_f4b081a27ffe…`); an explicit `run_id` is 1–64 characters of `A-Z a-z 0-9 . _ -`, must not start with `.`, and must not contain `..`. `open-gajae-explore`, `open-gajae-document-specialist`, `open-gajae-executor`, and `open-gajae-cleaner` have the tool denied and hidden. The plugin's `context` hook also removes it from the requests of host agents such as `build` and `general` and of user-defined agents, and the tool refuses them if called (see [Accepted behavior differences](#accepted-behavior-differences)).

```text
<worktree>/.open-gajae/
  _session-<created>-<session-id>/
    plans/ralplan/<run-id>/
      stage-01-planner.md
      stage-01-intent.md
      stage-01-architect.md
      stage-01-critic.md
      stage-02-revision.md
      …
      stage-NN-final.md
      index.jsonl
      pending-approval.md
    state/ralplan-state.json
    state/ralplan-continuation.json
    state/audit.jsonl
    state/active/ralplan.json
    state/skill-active-state.json
```

- **Stage files.** Stages are `planner`, `intent`, `architect`, `critic`, `disposition`, `revision`, `post-interview`, `adr`, and `final`; `stage_n` (1–999) is the pass number. Each write creates an immutable `stage-NN-<stage>.md` and appends one row `{stage, stage_n, path, created_at, sha256}` to the run's `index.jsonl` ledger; the `final` row also carries `auto_handoff`. `final` is copied to `pending-approval.md`, which the next `final` overwrites. There are no link rules, generated index pages, or generated headers.
- **Idempotent writes.** Rewriting the same `(stage, stage_n)` with identical content returns the earlier receipt with `deduplicated: true` (and restores a missing ledger row); different content is refused with "Use a new stage_n to record another pass."
- **Roles write content only.** The planner, architect, and critic pass the whole artifact as `content` and return only the receipt to the primary. The primary may pass `content`, or a `path` to a file under an OS temp root (`os.tmpdir()`, `$TMPDIR`, `/tmp`, `/var/tmp`, and their `/private` aliases) outside the project.
- **Dispositions.** When Architect and Critic findings conflict, a `disposition` stage (JSON, GJC's `ralplan.review_conflicts.v1` schema) must resolve each conflict before revision; the tool checks its source receipts against the run's ledger and refuses open, unknown, or mismatched entries.
- **Bookkeeping.** `state/audit.jsonl` gets one row per file change. `state/active/ralplan.json` and the `state/skill-active-state.json` snapshot hold the active row and its HUD chips; nothing in open-gajae draws them yet (Mandatory follow-up development, item 6). `state/ralplan-continuation.json` holds only the continuation breaker counter.

**Budgets and PLANNING-STUCK.** A run opens at most `ralplan.maxIterations` passes (planner and revision openers, default 5), counted from `index.jsonl` or from the stage files on disk, whichever is larger. Each lane may write `ralplan.maxReviewPassesPerLane` architect or critic passes per opened pass (default 1). A write over either budget returns a `PLANNING-STUCK` result (`ok: false`, `planning_stuck: true`, `marker: "PLANNING-STUCK"`) instead of an error, and the state records `planning_stuck`. Architect and critic writes inside an already opened pass, and `post-interview`, `adr`, and `final`, still go through, so the best plan can be kept as `pending approval`; a stuck run's `final` resolves `auto_handoff` to `off` with reason `planning_stuck` and is never dispatched. A new `run_id` starts a fresh folder and budget.

**Consensus flow.** The skill follows GJC's nine steps. The planner drafts (`planner`, pass 1). The primary reconciles material intent with the user (`intent`), one native `question` at a time, and resumes the planner for a `revision` if the contract changed. The architect and a plan-only critic review pass 1 in parallel (two `subagent` calls in one message) and record `lane_verdict` (`CLEAR`/`WATCH`/`BLOCK`, `OKAY`/`ITERATE`/`REJECT`). Pass 2 and later resume the same planner, architect, and critic sessions (`subagent` with the recorded `sessionID`) and review sequentially, architect then critic. After consensus the primary checks new intent deltas with the user (`post-interview`) and writes `final` with its ADR. `--interactive` adds a draft review; `--deliberate` adds a pre-mortem and an expanded test plan, and it auto-enables on explicit high-risk signals. No continuation fires while a question is open, because the native `question` tool holds execution until it is answered — no `session.execution.succeeded` is published in the meantime.

The tool records each role's own session ID when that role writes (`planner_subagent_id`, `architect_id`, `critic_id`), so the primary can resume it. When a resume fails, the primary starts a fresh role session and records `fallback_reason`, `fallback_attempted_id`, and `fallback_stage_n`.

**Approval, Stop here, and handoff.** If `final` resolves `auto_handoff.effectiveTarget` to `ultragoal` (with `ralplan.autoHandoff: "ultragoal"` set and the run not stuck), the primary hands off without asking. Otherwise it asks one `question` offering **Refine further**, **Approve execution via ultragoal (Recommended)**, and **Stop here**, plus free text. The plan stays `pending approval` unless the user approves or has already named ultragoal in the same turn.

- **Refine further** returns to the re-review loop.
- **Stop here** is `ralplan state(patch={"active": false})`: the phase stays `final`, `pending-approval.md` is kept, and the active row is removed. Asking for ultragoal later loads it directly, as in GJC: `ralplan handoff` refuses an inactive ralplan (R-OD18), so ultragoal carries no `handoff_from`.
- **Approve execution via ultragoal**: the primary calls `ralplan handoff(to="ultragoal")`, loads the `ultragoal` skill, reads the final plan (the result names its `pending-approval.md`), and calls `ultragoal create` with the plan's description and goals as structured arguments. The handoff op requires an active ralplan in a terminal phase (`final`, `handoff`, `complete`, `completed`, `failed`, `cancelled`, `canceled`, `inactive`); an inactive one is refused (R-OD18). It runs the shared journaled handoff (see [Ultragoal](#ultragoal)): ralplan becomes `{active: false, current_phase: "handoff", handoff_to: "ultragoal"}` and its active row stays as an inactive `handoff_to` row, and ultragoal becomes active in `goal-planning` with `handoff_from: "ralplan"`, both over their kept fields.
- **Same-execution gate.** Loading `skill` `ultragoal` in the same execution in which `ralplan` was loaded performs that handoff itself when ralplan is active in a terminal phase (for example the active `final` while the approval question is open), and is refused while ralplan is active in a live planning phase. In a later execution — after a continuation or a background subagent's completion resumed the session — the load enters ultragoal without a handoff and leaves ralplan as it is, so after `final` call `ralplan handoff(to="ultragoal")` first (a known behavior; see [Ultragoal](#ultragoal)).
- **The reverse.** `ultragoal handoff(to="ralplan", reason)` runs the same journaled handoff the other way: ultragoal goes to `handoff` (its goals, ledger, progress, and the goal are kept), and ralplan becomes active in `planner`, keeping its recorded `run_id`. Do not call `ralplan start`; continue the run with `ralplan write`, using the next unused `stage_n`, or pass a new `run_id` on the first `write` for a fresh folder and budget. After the new `final`, `ralplan handoff(to="ultragoal")` returns to ultragoal's `goal-planning`, and `ultragoal create` replaces the goal list.

**Write semantics (as in GJC).** A `write` without a prior `start` creates the state (`active: true`, phase = the stage written, no `mode`, `interactive`, or repository binding). A `write` with a new explicit `run_id` switches the run and resets the verdict, stuck, and auto-handoff fields. On the same run, a write sets `active: true` and advances the phase to the stage written, unless the phase is locked (`final`, `handoff`, `complete`, …): then the state is left untouched, so refinement writes after Stop here or `clear` do not reactivate the run. A write still rewrites the active row, which stays until the next Stop here, handoff, or clear. `write` is not refused while ultragoal runs: a role's or the primary's write during an ultragoal run can activate ralplan. Ultragoal stays the visible primary skill while its row is active, but once its row is gone (the run completes or is cleared) the ralplan row becomes the primary skill: the planning guard then blocks edits, and once no goal is active, ralplan continuation resumes. Recover with `ralplan state(patch={"active": false})` or `ralplan clear`; the guard's block message names both.

**Planning guard.** While ralplan is the root session's visible primary skill and its state is `active: true` in a phase other than `complete`, `completed`, `failed`, `cancelled`, `canceled`, or `inactive` — so `final` and `handoff` still block while active — `write`, `edit`, and `patch` are refused for every agent in that session lineage unless every target is under an OS temp root outside the project. The primary skill is the highest-ranked active row, where the planning pipeline deep-interview → ralplan → ultragoal collapses to its latest stage (GJC's rank). While ultragoal is the primary skill the ralplan guard does not apply; ultragoal's own guard blocks the same calls during its `goal-planning` phase instead. The guard does not inspect `shell` commands. Deep-interview specs are written by the `deep-interview` tool, so the guard does not affect them. Independently of the guard, every agent is always refused `write`, `edit`, and `patch` on a session folder's `plans/ralplan/**`, `state/**`, and `specs/deep-interview-*`, and on ultragoal-owned files; only the tools change them.

Continuation re-prompts the session on the durable `session.execution.succeeded` event (v2 does not publish `session.idle`) via `ctx.session.synthetic({ resume: true })`, while ralplan is the visible primary skill (its active row; ralplan deviation 10) and its state is active, not in a terminal phase, and not `planning_stuck`. While the goal is active, the goal loop takes the turn instead and ralplan gets no continuation (see [Ultragoal](#ultragoal)). A circuit breaker stops reinforcement after 30 injections, and the breaker counter, kept in `state/ralplan-continuation.json`, expires after 45 minutes, unchanged from v1's constants; exhaustion sets ralplan `active: false` and writes one audit row. When the user interrupts a turn — `session.execution.interrupted` with reason `user` (Esc, or the interrupt API) or `shutdown` (a dismissed `question` form, and the host's default reason-less interrupt) — a stop mark is set; only the next real user prompt clears it. Reasons `inactivity` and `superseded` do not set the mark. Continuation also skips while an owned background subagent session (launched with `background: true`) is still running under the current session, tracked from `session.created`/`session.execution.started`/terminal events by `parentID` (OMC/OMO parity; v1 had no background-subagent case). When such a child finishes, the host's own subagent-completion synthetic resumes the parent, and that later `succeeded` is judged like any other, bounded by the same breaker. Because a v2 plugin instance is created per location on a shared server and every instance receives every server event, this plugin only acts on sessions whose location matches its own — a fact new to v2, not a change to any of the decisions above.

When the host compacts a session whose ralplan state is active, the plugin adds one `<ralplan-compaction-context>` block to the compaction prompt with the current plan's goal, scope, non-goals, acceptance criteria, Intent Reconciliation, and next action. Nothing is added when the state is inactive or corrupt or the artifact's sha256 no longer matches its ledger row. State is per-session; there is no cross-session resume and no ralplan restore notice.

**Known behavior (as in GJC).** After a write on a locked phase — refinement after `final`, or a write after Stop here or `clear` — the active row's phase is the stage just written while the state's phase stays `final` or `complete`. `ralplan doctor`, which reads the raw row files, then reports `stale_active_state` with `ralplan clear` as its fix command, as GJC does; after refinement on `final` that unforced `ralplan clear` succeeds, also as in GJC, because `clear` reads a locked state's phase in place of the row's (after a `clear` the state is already terminal, so an unforced clear is refused). This is expected: do not call `ralplan clear` on that report alone, because clearing ends the run.

**Known behavior (as in GJC): transition audit rows.** A write whose stage is not a table edge from the current phase still succeeds; it only appends an `invalid_transition_detected` row to `state/audit.jsonl` (spec D-T11). The skill's own order produces such rows routinely, because the table lacks these edges: parallel pass-1 reviews land in either order (`intent→critic`, `revision→critic`, `critic→architect`), pass 1 can reach consensus with the Architect last (`architect→post-interview`), a revision follows the last review lane (`architect→revision`), pass 2 goes from the revision straight to the Architect (`revision→architect`), and step 7 writes `final` right after `post-interview` (`post-interview→final`, since the table routes `final` through `adr`). GJC's table and skill are the same, so GJC writes the same rows for the same order.

**No progress display.** The TUI sidebar the spec planned for ralplan (D-H3–D-H7) is deferred (R-OD17): the distributed OpenCode 2.0.15 binary does not give a TUI plugin the host's `solid-js` and `@opentui/*` instances, so a plugin cannot draw with ordinary imports (Mandatory follow-up development, item 6). The ralplan active row and snapshot still carry GJC's HUD chips.

## Ultragoal

`ultragoal` is durable multi-goal execution rebuilt on GJC's ultragoal runtime and goal mode at the GJC pin: `skills/ultragoal/SKILL.md`, the `ultragoal` tool in `src/ultragoal-runtime/`, the `goal` tool and the goal loop in `src/goal/`, the shared active-row, snapshot, audit, journal, handoff, and doctor base in `src/skill-state/`, and the `open-gajae-cleaner` prompt. It replaced the Phase 1 port of OMC ralph; only the `progress.txt` log format (`src/ultragoal-runtime/progress.ts`) is still OMC-derived. Every difference from GJC is recorded in [Deviations from GJC (ultragoal)](#deviations-from-gjc-ultragoal); the SKILL's and prompts' source sections cite those row numbers. The design decisions are in `.omc/specs/deep-interview-ultragoal-gjc-revision.md` (with its Errata E1–E6), `.omc/plans/ralplan-ultragoal-gjc-revision.md`, and `.omc/plans/ultragoal-gjc-pq-decisions.md`.

How the current implementation works, step by step down to the functions that do each step, is in [`docs/skills/ultragoal/`](docs/skills/ultragoal/README.md).

**Entry and goal planning.** The `ultragoal` keyword and an `@ultragoal` mention only add a notice (`open-gajae: ultragoal keyword notice added` / `mention notice added`) asking the model to load the skill. A native `skill` call with id `ultragoal` from `open-gajae` enters it: a missing or inactive ultragoal state — including a completed or handed-off one — is raised to `goal-planning` with its fields kept, and an active one keeps its phase (deviation 35). Loaded in the same execution as `ralplan`, it first hands off an active ralplan in a terminal phase, and it is refused while ralplan is active in a live planning phase (see [Ralplan](#ralplan)). Loaded in the same execution as `deep-interview`, it passes the deep-interview gate instead: an interview still `interviewing` refuses the load, one on `handoff` is handed off, and a finished one with a valid spec is linked — which returns even an active run to `goal-planning` (see [Deep interview](#deep-interview)). While ultragoal is the visible primary skill and its state is active in `goal-planning`, `write`, `edit`, and `patch` from every agent of the session lineage are refused unless every target is under an OS temp root (GJC's goal-planning mutation guard); `create` ends goal planning. There is no `start` op: to run again, load the skill and call `create`.

**Storage.** All files belong to the session lineage's root session, so role subagents read and report into the root's folder:

```text
<worktree>/.open-gajae/
  _session-<created>-<session-id>/
    ultragoal/goals.json
    ultragoal/ledger.jsonl
    ultragoal/progress.txt
    state/ultragoal-state.json
    state/goal-state.json
    state/goal-continuation.json
    state/active/ultragoal.json
    state/skill-active-state.json
    state/audit.jsonl
    state/transactions/<mutation-id>.json
```

- `ultragoal/goals.json` (version 2) holds the run's `description` and its goals `G001`, `G002`, … with `title`, `description` (the goal's objective), `status` (`pending`, `active`, `complete`, `failed`, `blocked`, `review_blocked`, `superseded`), `acceptanceCriteria` (`[{id, text}]`, IDs `G001.AC1`, …), `amendments` (the original text of every accepted change), a fix goal's `steering`, and a completed goal's `completionVerification` receipt. A version 1 file — the retired OMC ralph format — is refused; there is no migration.
- `ultragoal/ledger.jsonl` is the audit trail: one JSON row per event with `eventId` and `timestamp` — `plan_created`, `goal_started`, `goal_checkpointed` (with the gate as `qualityGateJson` and the receipt), `steering_accepted`, `review_blockers_recorded`, `blocker_classified`, `critic_verdict`, `workflow_handoff` — and GJC's `{type: "reconcile_failed", error}` row when a reconcile fails. Refused ops, `add_pattern`, and read ops write no row.
- `ultragoal/progress.txt` is OMC ralph's progress log: `## Codebase Patterns`, one entry per complete checkpoint (implementation, files changed, learnings), and `PLAN` and `HANDOFF` notes. `create` appends to it rather than replacing it.
- `state/ultragoal-state.json` is the mode state, rewritten from `goals.json` and the ledger by every reconciling op; `state/active/ultragoal.json` is its active row with GJC's HUD chips (blocked, goals, current, status, ledger), which nothing draws yet, and `state/skill-active-state.json` the ranked snapshot.
- `state/goal-state.json` is the goal (below); `state/goal-continuation.json` is the goal loop's hook-only counter and hold, not audited.
- `state/transactions/` holds the journal of a cross-skill handoff while it runs. It is evidence only: nothing replays or rolls it back, and `doctor` does not read it (GJC's doctor does not report a pending journal either).
- `state/audit.jsonl` gets one row per write of the ultragoal files, the mode state, the row, the snapshot, the journal, and the goal state; only `state/goal-continuation.json` is not audited.

Only the `ultragoal` and `goal` tools change these files: `write`, `edit`, and `patch` on them are refused for every agent.

**The `ultragoal` tool** belongs to `open-gajae` alone: it is hidden from, and refused to, every other agent. Every op works on the lineage root and runs in the session's one workflow queue; it validates everything before its first write and then writes in GJC's order (plan, ledger, progress, goal state, reconcile). Results are GJC's human-readable text, not JSON; a refusal is `Error: <message>`, and GJC command names become op calls such as `ultragoal next` or `ultragoal record_review_blockers`.

| Op | Input | Effect and result |
|---|---|---|
| `status` | — | GJC's status text (`# ultragoal status`, `- status:`, `- goals: N (…)`, `- objective:`, `- current:`, `- goals_path:`, `- ledger_path:`), then `- run_complete: yes` or `no (<reason>)`, `- goal: <status> (<source>)` or `- goal: none`, and a `## goals` list with each goal's receipt state (`valid`, `per-goal(superseded final)`, `stale`, `none`) and active criteria. |
| `create` | `description`, `goals[]` of `{title, description, acceptanceCriteria[]}` (at least one goal, each with a criterion) | Overwrites `goals.json` with every goal `pending`, appends `plan_created` and a `PLAN` note, and arms the goal. `Created ultragoal plan with N goal(s) at <path>.`, then `Goal armed: …` or `Goal not armed: …`. |
| `next` | `retry_failed?` | Activates the next goal (`goal_started`): the active one, else the first pending one; with `retry_failed` and no active goal, the first failed goal before any pending one. Prints `ultragoal next-action=execute-goal goal-id=…`, `objective=`, `goal-objective=`, `checkpoint requires=`, and `criteria=`; or `ultragoal complete all=true`, with `run-complete=no reason=…` and a reopen `hint=` when the receipts do not close the run; or a `retry-failed` or `resolve-blockers` action. |
| `checkpoint` | `goal_id`, `status` (`complete`, `failed`, `blocked`, `pending`), `evidence`; for `complete` also `gate`, `implementation[]`, `files_changed[]`, `learnings[]` | `complete` validates the gate, writes the receipt, supersedes a fix goal's `review_blocked` parent, appends a progress entry, and activates the next goal; `failed` and `blocked` record the status; `pending` reopens a goal from any status. Appends `goal_checkpointed`. Prints `Checkpointed <id> as <status>.` with GJC's follow-up lines, `Criteria:` for the next goal, `Run not complete: <reason>`, or `Reopened <id>; …`. |
| `validate_gate` | `gate`, `goal_id?` | The same gate rules as `checkpoint(complete)`, read-only: `quality gate is valid.` or `N quality-gate error(s):` with one `  path [code]: message` line per defect. Without `goal_id` it checks the first pending, active, or failed goal; with no plan or no such goal it checks the gate's shape only, as a per-goal gate. |
| `add`, `revise`, `supersede` | `target` (`goal` or `criterion`), `goal_id`, `criterion_id`, `title`, `description`, `acceptanceCriteria`, `criterion`, `after`, `rationale`, `evidence` | Plan changes (below). Appends `steering_accepted` and keeps the original in `amendments`. `Accepted <op> steering. target=<id>`. |
| `add_pattern` | `pattern` | Adds a Codebase Patterns line to `progress.txt`. |
| `record_review_blockers` | `goal_id`, `title?`, `objective`, `evidence` | Sets the goal `review_blocked` and appends a fix goal (below). `Recorded review blockers. blocker-goal-id=<id>`. |
| `classify_blocker` | `classification` (`resolvable`, `human_blocked`), `evidence`, `goal_id?` | Appends `blocker_classified`. `Recorded blocker classification: <c> event-id=<id>.` |
| `record_critic_verdict` | `terminus` (`completion`, `pause`), `verdict` (`OKAY`, `ITERATE`, `REJECT`), `evidence`, `blockers[]`, `classification_event_id?`, `goal_id?` | Appends `critic_verdict`. Prints the verdict and `critic non-OKAY streak: n/5`, with `— continuation held` at 5. |
| `handoff` | `to` (`ralplan`, `deep-interview`), `reason` | The journaled handoff (below). One-line JSON receipt. |
| `doctor` | — | GJC's doctor text over the ultragoal state, row, and snapshot; changes nothing. |
| `state` | `patch` | Merges fields into the ultragoal state (`null` deletes a field). Derived fields (`goals`, `counts`, `status`, `active_goal_id`, the paths, `latestLedgerEvent`, `skill`, `version`, `session_id`) are refused, and a `current_phase` change must be an edge of GJC's transition table. One-line JSON receipt. |
| `clear` | `force?` | Sets `{active: false, current_phase: "complete"}` over the kept fields; the files are kept and the row is removed. Without `force` it refuses a corrupt state, a state already in a release phase (such as `complete` or `failed`), and a row whose phase differs from the state's. One-line JSON receipt, plus `The goal is still <status>; run goal drop to end it.` while the goal is open. |

Every other op — `status`, `create`, `next`, `checkpoint`, `add`, `revise`, `supersede`, `record_review_blockers`, `classify_blocker`, and `record_critic_verdict` — then reconciles: it derives the run status from `goals.json` and the ledger and force-writes the mode state, the active row, the snapshot, and the HUD. `add_pattern`, `validate_gate`, and `doctor` do not reconcile, and `state`, `clear`, and `handoff` write the row themselves.

**Goals and plan changes.** Plan changes need a `rationale` and `evidence` of at least five words and 32 characters each. A revised criterion gets a new ID and its old ID is retired, never reused. The allowed statuses follow GJC's steering ops (deviation 38):

- A goal's wording, its position (`revise` with `after`), and its criteria change only while the goal is `pending`; an `active` or `failed` goal is first moved back with `checkpoint(status: "pending")`.
- A goal `supersede` accepts a `pending`, `blocked`, or `review_blocked` goal, and is refused for the only remaining required goal; a criterion `supersede` is refused for the goal's last active criterion.
- A goal `add` goes right after the goal named by `after`, or at the end; no call places a goal first.
- A `complete` goal cannot be changed at all. To change and re-verify one, reopen it with `checkpoint(status: "pending")`, change it, call `next`, and checkpoint it `complete` with a new gate. `checkpoint(failed|blocked)` and `record_review_blockers` also move a goal out of `complete`, as in GJC.

**Verification.** Every goal gets its own architect review before it is checkpointed `complete`; the heavyweight review runs once, at the run's final required goal — the goal whose completion leaves no other required (not superseded) goal unfinished. `next`'s `checkpoint requires=` line says which gate a goal needs.

- The per-goal gate is `targetedVerification` (`passed`, at least one command, evidence), `architectReview` (`architectureStatus`, `productStatus`, and `codeStatus` all `CLEAR`, `recommendation: "APPROVE"`, evidence, no blockers), and `criteriaCoverage` with exactly one row per active criterion (`covered`, `passed`, or `verified`). A non-clean review is checkpointed `failed`, fixed, and retried with `next(retry_failed: true)`; there is no retry cap.
- The final gate adds `reviewCohort` — `reviewGeneration`, `joined: true`, and three lanes run on one frozen change set: the read-only `open-gajae-cleaner` (`PASS`), an `open-gajae-architect` (`CLEAR`), and an `open-gajae-executor` QA/red-team lane (`passed`, with `commands` and `adversarialCases`) — and `criticReview` (`OKAY`) from the terminal `open-gajae-critic`. A second or later generation needs `deltaOnly: true` and `deltaPaths`. Unknown top-level keys are refused, and a refused gate lists every defect at once.
- An `open-gajae-executor` assignment that contains `[ultragoal-red-team]` gets GJC's executor red-team fragment appended by the plugin; without the marker the executor works as usual.
- **Fix goals.** A cohort with blockers is recorded as one batch with `record_review_blockers`: the goal becomes `review_blocked` and a fix goal is appended with the default title `Resolve final code-review blockers` and one criterion, `<objective> is resolved and re-verified` (`objective` at most 1972 characters). The same trimmed objective for the same blocked goal returns the open fix goal; a fourth unresolved fix goal for one blocked goal is refused (`review_blocker_recursion_cap`). Completing a fix goal supersedes its `review_blocked` parent, and its gate is judged with the parent already superseded, so a run-closing fix goal needs the final gate from its first checkpoint.
- **Terminal critic.** A completion-side `ITERATE` or `REJECT` is recorded with `record_critic_verdict` first. Five non-OKAY verdicts in a row — counted after the last OKAY (an OKAY verdict, or a final checkpoint whose gate carries `criticReview` OKAY) and after the latest `create`, both termini together — hold the goal loop until the next user prompt. The gates do not change, and there is no override op.
- **Pause.** `goal pause` is refused while the run is not complete unless the latest `blocker_classified` event is `human_blocked` and a later clean pause `critic_verdict` (`OKAY`, evidence, no blockers) is bound to it through `classification_event_id`.

**Receipts and run completion.** A complete checkpoint writes the receipt `completionVerification` — `receiptId`, `receiptKind` (`per-goal` or `final-aggregate`), `criteriaRevision` (a hash of the active criteria), `qualityGateHash`, `checkpointLedgerEventId`, and `verifiedAt` — to the goal and to its `goal_checkpointed` event. A receipt is valid while the goal's receipt matches its ledger event and its active criteria are unchanged; a final receipt is also staled by a later change to the required-goal set (`plan_created`, a goal `add` or `supersede`, `review_blockers_recorded`), and such a final still counts as a per-goal completion. The run is complete when every required goal is `complete`, each receipt is valid, and the most recently completed goal holds a valid final receipt. File statuses alone can show every goal complete — the phase is `complete` and the row is gone — while the run is not; then `status` prints `run_complete: no (<reason>)`, `goal complete` is refused, and the fix is to reopen the last completed goal and re-verify it with the final gate.

**The `goal` tool** is GJC's goal-mode tool with the ops `get`, `create` (`objective`), `complete`, `resume`, `drop`, and `pause`, and it belongs to `open-gajae` alone. The goal lives in the root's `state/goal-state.json` as `{version, id, objective, status (active, paused, complete, dropped), source (ultragoal or user), created_at, updated_at}`. Results are GJC's text: `Goal: <objective>` and `Status: <status>`, or `No active goal.`; refusals are GJC's (for example `cannot create a new goal because this session already has a goal`).

- `drop` keeps the file with `status: "dropped"`, and every op then treats it as no goal: `get` says `No active goal.` and `resume` is refused.
- `complete` and `pause` run the ultragoal guards before looking up the goal, whatever the goal's source. `complete` is refused while an ultragoal plan exists whose run is not complete; when a receipt is the cause, the refusal names the goal to reopen with `ultragoal checkpoint(status: "pending")`. `pause` is refused unless the pause gate above is met. `drop` has no guard.
- `ultragoal create` arms the goal: with no open goal (none, complete, or dropped) it creates a `source: "ultragoal"` goal with the fixed objective "Complete the durable ultragoal plan in `.open-gajae/_session-<created>-<id>/ultragoal/goals.json`, including later accepted/appended goals, under the original description constraints; use `.open-gajae/_session-<created>-<id>/ultragoal/ledger.jsonl` as the audit trail." (the real folder name); it keeps an open goal whose source is `ultragoal` or whose trimmed objective is that text; with another open goal it arms nothing and says so. No other ultragoal op or hook changes the goal.

**The goal loop.** On each `session.execution.succeeded` of the lineage root while the goal is active — whatever the agent — the plugin skips when a continuation is already in flight, after an Esc, or while a background child is running, and otherwise inserts a `<goal-continuation>` message (`resume: true`, TUI line `open-gajae: goal continuation`) with GJC's continuation reminder. There is no iteration cap.

- **Holds.** Three turns in a row without a tool call, or a critic non-OKAY streak of 5, hold the loop. The hold posts one `<goal-notice>` (`resume: false`, TUI line `open-gajae: goal continuation held (<reason>)`) that names the cause and says that sending a message continues; the goal stays active. The next real user prompt at the root releases it, sets the tool-less count to 0, and, for a critic hold, restarts the critic count. The counter and the hold live in `state/goal-continuation.json`, which starts over for a new goal.
- **Esc.** An interrupt with reason `user` or `shutdown` stops the loop until the next real user prompt; that turn's end resumes it.
- **Ralplan and deep-interview.** While deep-interview is the visible primary skill, active on `interviewing` or `handoff`, it decides the turn first and the goal loop is skipped (an exception to spec D-TL6, deep-interview deviation 16); otherwise, while the goal is active, the goal loop alone decides the turn, held or not, and ralplan continuation runs only when no goal is active.
- **Goal context.** On a root `open-gajae` request while the goal is active, a `<goal-context>` block (GJC's goal-mode prompt) is added before the prompt unless the request already carries the same text as a single-part user message, and kept as a `synthetic({ resume: false })` message (TUI line `open-gajae: goal context added`) — once per goal, and again after a compaction drops it.
- **Compaction.** While the ultragoal row is active in a phase outside `missing`, `failed`, `complete`, and `handoff`, and the goal is not paused, the compaction prompt gets an `<ultragoal-compaction-context>` block: the objective, criteria, current goal, progress, next action, the Codebase Patterns and recent learnings, and a `STALLED` line when durable progress has not changed across compactions.

**Handoff.** `ultragoal handoff(to: "ralplan" | "deep-interview", reason)`, `ralplan handoff(to="ultragoal")`, and the same-execution `skill ultragoal` gate share one journaled transaction (GJC's `state handoff` verb): it writes the journal, merges the callee over its kept fields (`active: true`, its first phase — ralplan `planner` with its `run_id` kept, deep-interview `interviewing` — `handoff_from`, `handoff_at`), merges the caller (`active: false`, `current_phase: "handoff"`, `handoff_to`, `handoff_at`), keeps the caller's row as an inactive `handoff_to` row, writes the callee's active row and the snapshot, and, when ultragoal hands off, appends `workflow_handoff` and a `HANDOFF` note; then it marks the journal committed and removes it. The goal is left as it is, so the goal loop keeps prompting while planning. While ultragoal is the visible primary skill, loading `skill` `ralplan` or `deep-interview` is refused with an `ultragoal handoff` hint. After ralplan's approval, ultragoal returns to `goal-planning` and `create` replaces the goal list; the ledger and `progress.txt` keep the history.

## Owned roles and settings

- **`open-gajae`** is the primary. It owns edits, decisions, integration, and the workflow tools. No rules are added beyond the host defaults.
- **`open-gajae-explore`** investigates repository facts read-only. It cannot edit, delegate (`subagent`), ask questions (`question`), or use the workflow tools. It keeps full `shell` access (OMC parity — no `shell`/Bash rule is added for any role).
- **`open-gajae-document-specialist`** researches documentation and citations. It cannot edit, delegate, ask questions, or use the workflow tools. Its `chub` protocol is documented as read-only in its prompt; the host permission rules do not restrict `shell` to only `chub` commands.
- **`open-gajae-planner`**, **`open-gajae-architect`**, and **`open-gajae-critic`** are the ralplan consensus roles. All three run as `mode: subagent` and carry no default model; set one through the settings `agents` map. Their prompts are GJC's planner, architect, and critic roles with host substitutions. None of the three can edit: each records its stage artifact with `ralplan write` (`content` only) and may use `ralplan status` and `ralplan state`; `edit` is denied, as are `question` and `deep-interview`. Architect and critic also have `subagent` denied. The planner delegates research: its `subagent` permission allows only `open-gajae-explore` and `open-gajae-document-specialist`. `question`, `deep-interview`, and both Code Mode session tools (`opencode_session_move`, `opencode_session_rename`) stay denied for all eight subagent roles. `subagent_depth` is not raised by the plugin; set `experimental.subagent_depth: 2` in host config yourself (see Install).
- **`open-gajae-executor`** (ported from OMC's `agents/executor.md`) implements bounded code changes that the `ultragoal` leader delegates, and runs the boundary cohort's QA/red-team lane when its assignment carries `[ultragoal-red-team]` (the plugin then appends GJC's red-team fragment). It cannot ask questions (`question` denied) and cannot use the `ultragoal` or `goal` tools; its only delegation is `subagent` to `open-gajae-explore` for codebase lookups and `open-gajae-architect` after repeated failures on the same issue. It keeps `edit` and `shell`.
- **`open-gajae-cleaner`** is the read-only cleaner lane of ultragoal's boundary review cohort. Its prompt is GJC's ultragoal `ai-slop-cleaner` fragment, with a few read-only sentences kept from the earlier OMC-based cleaner prompt. It cannot edit, write, patch, delegate, ask questions, or use the workflow tools; it keeps `shell` for inspection and reports blocking and advisory findings in an `AI SLOP CLEANUP REPORT` ending in `Gate Result: PASS` or `BLOCKED`, without changing anything.
- **`open-gajae-lateral-reviewer`** runs the deep-interview lateral review panel's personas (researcher, contrarian, simplifier, architect), several in parallel. Its prompt is GJC's panel fragment, which asks for one JSON object; each call passes only the persona and the interview context, and advisory lanes do not use this role (deep-interview deviation 27). It takes the default read-only role rules (no `edit`, `subagent`, `question`, or workflow tools; `shell` is not restricted, as for every role) and carries no default model (deep-interview deviation 37).
- `ultragoal`, `goal`, and `deep-interview` belong to `open-gajae` alone: every owned role has them denied, and the plugin hides them from every other agent. Within ultragoal, `open-gajae-architect` reviews each goal and the cohort's frozen change set, and `open-gajae-critic` is the terminal critic; both return their verdict in their response, and the primary records it in the quality gate (`architectReview`, `reviewCohort`, `criticReview`) or with `ultragoal record_critic_verdict`.

Role rules are pushed onto each agent's `permissions` array after the host's own defaults, but **host `agents.<id>` permission rules from your config apply after the plugin's and win** — unlike v1, which reordered rules to keep a mandatory denial in force, a host override can loosen a role's default deny (a recorded deviation: "user config wins"). Settings are read from `~/.open-gajae/open-gajae.jsonc` and `<worktree>/.open-gajae/open-gajae.jsonc`. Fields merge project → user → defaults; unknown keys, invalid JSONC, or invalid values fail with diagnostics.

`deepInterview.ambiguityThreshold` is the deep-interview ambiguity threshold, GJC's default `0.05`, in `(0, 1]`; it is deep-interview's only setting. The primary receives the resolved value with its source (`~/.open-gajae/open-gajae.jsonc`, `./.open-gajae/open-gajae.jsonc`, or `default`) in its `<open-gajae-runtime-settings>` block; the source shortens the home path so the prompt carries no user name. A settings file that still has the removed round-cap key fails to load as an unknown setting; delete the key.

```jsonc
{
  "deepInterview": { "ambiguityThreshold": 0.05 },
  "agents": {
    "open-gajae": { "model": "provider/model", "variant": "variant-name" },
    "open-gajae-planner": { "model": "openai/gpt-6-luna" },
    "open-gajae-architect": { "model": "openai/gpt-6-luna", "variant": "high" },
    "open-gajae-critic": { "model": "openai/gpt-6-luna", "variant": "high" },
    "open-gajae-executor": { "model": "openai/gpt-6-luna", "variant": "medium" },
    "open-gajae-cleaner": { "model": "openai/gpt-6-luna", "variant": "medium" },
    "open-gajae-lateral-reviewer": { "model": "openai/gpt-6-luna", "variant": "medium" }
  },
  "ralplan": { "maxIterations": 5, "maxReviewPassesPerLane": 1, "autoHandoff": "off" }
}
```

There is no `ultragoal` setting: a settings file that still has an `ultragoal` key fails to load with `<file>.ultragoal: unknown setting`; delete the key. The goal loop has no iteration cap (see [Ultragoal](#ultragoal)).

| Setting | Default | Meaning |
|---|---|---|
| `deepInterview.ambiguityThreshold` | `0.05` | The interview's ambiguity threshold, in `(0, 1]`; `deep-interview start(threshold)` overrides it for one interview. |
| `ralplan.maxIterations` | `5` | Planner and revision passes one run may open, integer `1..20`. |
| `ralplan.maxReviewPassesPerLane` | `1` | Architect or critic passes per opened pass, integer `1..10`. |
| `ralplan.autoHandoff` | `"off"` | `"ultragoal"` hands a non-stuck `final` to ultragoal without the approval question. |

The `ralplan` keys merge per key like the other fields and are resolved once, when the plugin sets up in a location; restart the host after changing them. The `final` receipt's `auto_handoff.source` names the file whose `autoHandoff` value won, or `default`.

`variant` requires `model` on the same, already-merged entry: a user-level `model` plus a project-level `variant` is valid, but `variant` alone — in one file or split across both with no `model` anywhere — is rejected with an error naming the agent and asking to add `model "provider/model"`. This is stricter than the v2 host itself, which silently drops such a variant with a diagnostic. There is no provider fallback, tier mapping, or artificial collision rejection.

## Read-only code tools

The plugin registers eight read-only code tools (plus the `deep-interview`, `ralplan`, `ultragoal`, and `goal` tools above, twelve in total):

- `ast_grep_search` (`@ast-grep/napi` 0.31.1): AST search only; no replace.
- `lsp_goto_definition`, `lsp_hover`, `lsp_diagnostics`, `lsp_find_references`, `lsp_document_symbols`, `lsp_workspace_symbols`, and `lsp_servers`.

LSP servers are detected and reported, never downloaded. There is no LSP rename, code-action, or replacement suite. The actor set is all nine owned roles — `open-gajae`, `open-gajae-explore`, `open-gajae-document-specialist`, `open-gajae-planner`, `open-gajae-architect`, `open-gajae-critic`, `open-gajae-executor`, `open-gajae-cleaner`, and `open-gajae-lateral-reviewer` — matching OMC, where every agent can use the read-only LSP/AST tools. The project boundary replaces v1's per-call host permission ask: an input path is resolved against the host's current location directory, symlinks are followed, and the real target must stay inside the real project directory; `.env` and `.env.*` files are refused by both the requested and the resolved name, and `ast_grep_search` skips them during traversal too. Neither tool expands the explorer's permissions or grants arbitrary shell execution.

The only product environment knobs reached by source are `OPEN_GAJAE_LSP_TIMEOUT_MS`, `OPEN_GAJAE_LSP_IDLE_TIMEOUT_MS`, `OPEN_GAJAE_LSP_IDLE_CHECK_INTERVAL_MS`, `OPEN_GAJAE_LSP_CONTAINER_ID`, and `OPEN_GAJAE_PYTHON_LSP=basedpyright`. They are LSP implementation settings, not general configuration.

2. **Revise ultragoal the GJC way — resolved.** ultragoal now follows GJC's ultragoal runtime and goal mode: the reviewer brief and `record_verdict` are gone, the roles' own verdicts go into the quality gate, and tests run in the executor QA lane (see [Ultragoal](#ultragoal) and [Deviations from GJC (ultragoal)](#deviations-from-gjc-ultragoal)).
3. **Align the approval label — resolved.** `skills/ultragoal/SKILL.md` now names ralplan's approval option **Approve execution via ultragoal**, as GJC does.
4. **Known limits (recorded, not scheduled).** Several OpenCode processes working on one worktree are not serialized against each other: the plugin queues writes only within one process, while GJC uses file locks.
5. **Case-insensitive always-blocked paths.** The always-blocked path checks (`.open-gajae/_session-*/state/**`, `plans/ralplan/**`, and the ultragoal files) compare paths case-sensitively, so on a case-insensitive file system (the macOS default) a differently cased path such as `.OPEN-GAJAE/…` escapes them when the planning guard does not apply. Normalize case in these checks (maintainer decision R-OD13).
6. **TUI progress sidebar (deferred, R-OD17).** The ralplan sidebar the spec planned (D-H3–D-H7) was built on the port branch `feat/ralplan-gjc-stage-trail` (`tui-plugin/`, commit `96e9176`, fixed in `eb85dde` and `0cbb491`) and removed before the merge. In the distributed OpenCode 2.0.15 binary (compiled with Bun 1.4.2) the host does not map a TUI plugin's bare imports (`solid-js`, `@opentui/solid`, `@opentui/core`, `@opencode/plugin/tui`) to its own instances: without local packages the plugin fails to load, and with them it loads separate copies, so creating an element throws `No renderer found` and nothing is drawn. OpenCode's own test expects that mapping (`tui/test/plugin-source.test.ts`, "shared runtime and ordinary package identities survive plugin generations"), but it runs uncompiled. A manual check on 2026-09-29 drew the block when the plugin took the host instances from the host's virtual modules `opentui:runtime-module:<specifier>` (`@opentui/core` 0.5.10 `runtime-plugin.js`, an internal naming scheme). Re-add the sidebar once the host maps plugin imports, or with that workaround recorded as a host-integration deviation. It reads local files, so a TUI attached to a remote server stays unsupported.
7. **Tool hiding for deep-interview — resolved.** The `deep-interview` tool belongs to `open-gajae` alone and is hidden from every other agent, like the other workflow tools (deep-interview deviation 24); the former `state_*` tools are gone.

## Validation evidence and limits

The verification layers this port defines are: `bun run typecheck` and `bun test` on `@opencode/plugin` 2.0.15; unit tests for the prompt hook, permission-rule generation, continuation and the goal loop, tool hiding, the artifact guard, the code tools, the shared skill-state base, the `ralplan` tool and runtime (including key-set comparisons against GJC fixtures in `tests/fixtures/gjc-ralplan/`), the `ultragoal` and `goal` tools and runtime (checked line by line against their text results), and the `deep-interview` tool and runtime with its hooks (`tests/deep-interview-runtime.test.ts`, `tests/deep-interview-tool.test.ts`, the H-cases in `tests/hooks.test.ts`); host probes against a local OpenCode 2.0.15 binary (`tests/host-probe.ts`, `tests/host-session-probe.ts`, `tests/planner-permission-probe.ts`, `tests/package-probe.ts`, `tests/ralplan-trail-probe.ts`); and a manual checklist with `openai/gpt-6-luna` covering keyword entry, an Esc interrupt during ralplan, planner delegation with and without `experimental.subagent_depth`, one ralplan run through the stage files, Stop here, and the handoff, one ultragoal run through goal planning, the per-goal and final gates, reopening, the handoff to ralplan and back, a hold, and the hidden tools, and one deep-interview run through the basic flow and the lateral review panel (`docs/local-install-v2.md`, sections 5 and 7). Their current pass/fail status is tracked by the port's plan and ledger, not asserted by this document.

These layers are deterministic transport and source-contract checks using a fake provider where a host probe needs one; they are not actual-model behavior verification or proof of LLM obedience, prompt-branch guarantees, injection resistance, semantic model quality, external credentials, or installed language-server semantic correctness. Actual-model conversation checks for the GJC main prompt belong to the user, as specified in the GJC prompt plan's user-only checklist; they have not been performed here. LSP servers are never downloaded automatically. This guide records behavior and evidence scope; independent completion proof belongs in the durable delivery ledger.
